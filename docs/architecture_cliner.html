La question centrale : que fait CliNER ?

Un utilisateur arrive avec une question médicale (ex: "Essais cliniques cancer du poumon chez les adultes"). CliNER va :

  • Chercher sur ClinicalTrials.gov → récupérer les JSON des essais
  • Extraire les entités médicales (médicaments, critères, conditions) → NER avec Qwen Fine-Tuné
  • Répondre aux questions en langage naturel → Chatbot RAG avec BioBERT + Qwen

📥 Étape 1 — Ce qui entre : la Donnée Source

🌐 Source A — API ClinicalTrials.gov v2

Notre source principale. Streamlit construit une URL REST et la requête via requests.get().

Format entrant :

GET https://clinicaltrials.gov/api/v2/studies
  ?query.cond=lung+cancer
  &filter.advanced=AREA[Sex]FEMALE
  &pageSize=20
  &format=json

Format sortant : dict JSON avec pour chaque essai :

study = {
  "protocolSection": {
    "identificationModule": { # NCT_ID, titre
    "statusModule":         { # RECRUITING...
    "conditionsModule":     { # maladies
    "designModule":         { # Phase, StudyType
    "eligibilityModule":    { # age, sexe, criteres
    "armsInterventionsModule": { # medicaments
    "descriptionModule":    { # resume texte libre
  }
}

📄 Source B — PDF (fallback)

Si le JSON est pauvre ou si l'utilisateur force le mode PDF, on télécharge le document.

Format entrant : PDF binaire

Outil : PyMuPDF (fitz)

import fitz
doc = fitz.open(stream=content, filetype="pdf")
text = ""
for page in doc:
    text += page.get_text()  # str Python

Format sortant : str Python (texte brut)

⚠️ Pourquoi le JSON d'abord ?

Lire un PDF = lourd et lent. Le JSON ClinicalTrials contient déjà tout en texte structuré. PDF = dernier recours.

✂️ Étape 4 — Découpage en Chunks (LangChain)

Pourquoi découper ?

Un document de 10 000 caractères ne peut pas être donné d'un coup à BioBERT (limite 512 tokens) ni à Qwen (coût mémoire). On le coupe en chunks.

Règle de découpage :

  • chunk_size = 1000 caractères max
  • chunk_overlap = 200 caractères de chevauchement
  • Splitter intelligent : respecte les sauts de ligne

Résultat concret

Un document de 8 000 caractères → environ 9 à 11 chunks.


from langchain_text_splitters import (
    RecursiveCharacterTextSplitter)

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,
    length_function=len
)
chunks = splitter.split_text(text)
# chunks = ["NCT ID: ...", "Inclusion...", ...]

Format sortant : list[str]

🔢 Étape 5 — Vectorisation BioBERT (Embedding)

🧬 C'est quoi BioBERT ?

BioBERT (dmis-lab/biobert-v1.1) est un modèle NLP entraîné sur des millions d'articles PubMed. Il comprend le vocabulaire médical (dosages, termes latins, noms de médicaments).

Sa mission : transformer chaque chunk en un vecteur de 768 nombres flottants — une "empreinte digitale sémantique" du texte.

ENTRÉE
📝

Chunk de texte

Ex: "Inclusion Criteria: - ECOG 0-1 - Confirmed NSCLC..."

str (max 512 tokens)
→
TRAITEMENT
🧬

BioBERT (768M params)

  • Tokenisation (texte → token IDs)
  • Encodage (attention multi-têtes)
  • Mean pooling (moyenne des tokens)
  • Normalisation L2 (cosine similarity)
→
SORTIE
🔢

Vecteur 768D

Tableau de 768 nombres flottants = "empreinte médicale" du chunk.

[0.023, -0.147, 0.891, ..., 0.034]
# 768 valeurs entre -1 et 1
list[float] (768 valeurs)

💡 Pourquoi la similarité cosinus ?

Deux chunks sémantiquement proches auront des vecteurs pointant dans la même direction. L'angle = 0° → textes identiques. L'angle = 90° → textes sans rapport.
Ex: "critères d'inclusion médicament" et "eligibility criteria drug" → vecteurs très proches, même en langues différentes !

🗃️ Étape 6 — Stockage dans Supabase (pgvector)

Supabase = PostgreSQL managé dans le cloud avec l'extension pgvector qui stocke et cherche des vecteurs nativement en SQL.

TABLE : clinical_trials_data_biobert
doc_idTEXTNCT ID de l'essai (ex: "NCT04267848")
chunk_idTEXT (UNIQUE)"NCT04267848_chunk_0", "_chunk_1"...
raw_textTEXTLe texte brut du chunk (~1000 chars)
embeddingVECTOR(768)Le vecteur BioBERT (768 floats)
-- Insertion d'un chunk vectorise :
INSERT INTO clinical_trials_data_biobert
  (doc_id, chunk_id, raw_text, embedding)
VALUES (
  'NCT04267848',
  'NCT04267848_chunk_0',
  'Inclusion Criteria: - ECOG...',
  '[0.023, -0.147, 0.891, ...]'
)
ON CONFLICT (chunk_id) DO NOTHING;

Recherche sémantique (pgvector)

L'opérateur <=> de pgvector calcule la distance cosinus entre deux vecteurs directement en SQL.

-- Trouver les 5 chunks les plus proches :
SELECT raw_text
FROM clinical_trials_data_biobert
WHERE doc_id = 'NCT04267848'
ORDER BY embedding <=> '[0.02, ...]'::vector
LIMIT 5;

Ce que ça fait concrètement :

Compare le vecteur de la requête "inclusion criteria medications lung cancer" contre TOUS les vecteurs stockés. Retourne les 5 chunks les plus proches. En millisecondes.

✓ Résultat de l'Étape 6

Pour un essai avec 10 chunks → 10 lignes SQL avec texte brut + vecteur 768D. Prêt pour NER ou Chatbot.

💬 Étape 8 — Le Chatbot RAG (Retrieval-Augmented Generation)

🔑 RAG = Retrieval + Augmented + Generation

Pattern d'architecture IA qui empêche le LLM d'inventer des réponses. Il cherche d'abord les documents pertinents, les injecte dans le prompt, puis génère une réponse ancrée dans les faits.

❓ FAQ — Questions / Réponses Clés

Qu'est-ce qui est stocké dans Supabase ?

(1) Les chunks de texte bruts (raw_text), et (2) leurs vecteurs BioBERT (embedding VECTOR(768)). On ne stocke PAS les JSON originaux ni les PDFs dans la table vectorielle. Les PDFs sont dans un bucket S3 Supabase Storage séparé.

BioBERT et Qwen font la même chose ?

Non, rôles opposés :
• BioBERT = Retriever. Il ne génère PAS de texte. Il convertit en vecteurs pour la recherche sémantique.
• Qwen = Generator. Il ne fait PAS de recherche. Il lit les passages trouvés par BioBERT et génère une réponse (JSON pour NER, texte pour le chatbot).

Pourquoi fine-tuner Qwen sur CHIA ?

Un LLM généraliste sait parler de tout mais est moyen en extraction médicale. En le fine-tunant sur CHIA (textes d'essais cliniques annotés par des experts), on lui apprend à reconnaître précisément les entités biomédicales (Drug, Condition, Procedure...) et à les formater en JSON.

Qu'est-ce que vLLM ?

Moteur d'inférence optimisé pour les LLMs. Utilise la technique PagedAttention : gère la VRAM comme un OS gère la RAM. Résultat : 2 à 5× plus rapide que Transformers classique, capable de traiter plusieurs requêtes en parallèle.

Comment le RAG évite les hallucinations ?

Le prompt contient : "Réponds UNIQUEMENT en te basant sur les extraits ci-dessous. Si la réponse ne se trouve pas dans le contexte, indique clairement que tu ne possèdes pas l'information." Qwen ne peut pas inventer — soit l'info est dans les 5 chunks, soit il dit qu'il ne sait pas.

Qu'est-ce que le TF-IDF mentionné dans la présentation ?

TF-IDF est un algorithme de recherche classique (non-IA) basé sur la fréquence des mots. En combinant BioBERT (recherche sémantique) + TF-IDF (recherche lexicale exacte), on obtient un RAG Hybride plus robuste. Cette composante est en cours d'intégration par Jérémie.
